# Design reference and parity

## Behaviour

The design lives on a design canvas with one board for each screen family: Home, Peers and status, Exit nodes and routes, Sharing, Security, Network, Commands, Admin, Tools, Minecraft servers, the world generator, Settings, the library pages, overlays (palette, welcome wizard, context menu with live controls, appearance editor, super confirmation, unlock ladder, notices) the extensions manager and its permission review, and the website. Sixteen boards hold 51 views, and one more board records the every-surface sweep's before and after score. Each board can switch between its views and between dark and light themes. Overlays are drawn over the page they open on, one window tall, dimmed exactly when the app dims: dialogs, the welcome wizard and the palette over a scrim, menus, the floating editor and notices over the page as it is.

The boards are generated by `scripts/design-boards.mjs` from the app's own stylesheets (`tokens.css`, `app.css`, `mesh2.css`) and the shared page illustrations, so the design and the app use one design system. The checked-in copies live in `design/canvas/`. The stylesheets and the website hero's two captures (dark and light, made from the app's own `cli-set` screenshots) are uploaded to the canvas; `design/canvas/assets.json` maps each uploaded address to the snapshot file beside it, and the viewer serves those snapshots offline for the same addresses.

A static board cannot measure itself, so the viewer does it when it captures: it reports any segmented choice that wraps without the app's two-column layout and any in-page tabs that run past the edge without the arrow the app would show (or show it when they fit). The latest pass reports none.

The latest design pass was reviewed with a fresh-eye product-shot checklist; what it found and what changed is in `design/REHEARSAL.md`.

`tools/design-reference` is a plain developer viewer, not part of the app. It renders the checked-in boards offline, exactly as written. Animation is off, fonts are the vendored copies, and the screen, view, theme, size and scale come from its arguments:

```
npx electron tools/design-reference --board Peers.dc.html --view peers --theme dark --width 1440 --height 960 --scale 1 --capture out.png
```

`npm run design:parity` captures every view and its real counterpart (the app in capture mode, or the website) at 1440 by 960, scale 1, dark theme, motion off. The app's capture mode waits until the page is drawn and fully opaque before each picture and records whether it was; parity writes no evidence from a capture that never finished drawing. It writes:

- raw captures as lossless WebP;
- a labelled side-by-side comparison;
- a diff record with the changed-pixel ratio, a heatmap and the hashes of the board and both captures.

All of it goes to `docs/design-parity/captures/`.

## Inventory

`docs/design-parity/inventory.json` is written by hand. It lists every board view exactly once, with:

- its design-reference route and its real-app route;
- the state and the capture tuple;
- the Material Design 3 primitives it uses;
- its evidence paths;
- every reviewed deviation, with its reason and approval.

Screens that need a running Tailscale daemon record that the capture machine has none, so the app shows its real setup state there.

## When something goes wrong

`npm test` fails when a board view is missing from the inventory, a route or tuple field is missing, the audit or any evidence file is missing, a capture no longer matches its diff record, or a board changed after its evidence was captured. A negative test removes each kind of record in turn and expects the check to fail.

## Security and privacy

Captures come from a machine with no tailnet signed in, so they show no tailnet, token or personal data. The viewer blocks all network requests.

## How to verify

Run `npm run design:boards -- --check`, then `npm run design:parity`, then `npm test`.

## 廣東話摘要
